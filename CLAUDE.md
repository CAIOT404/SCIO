# SCIO: working rules for AI sessions

SCIO is a model-agnostic LangGraph framework that takes a software task from spec to a merged, tested, documented PR. Spec: `docs/PROMPT.md`. Design: `docs/ARCHITECTURE.md`. Evidence: `docs/RESEARCH.md`. Decisions: `docs/adr/`. Build it milestone by milestone (M0 to M5 in ARCHITECTURE.md section e); each milestone is its own branch, issue and draft PR.

## Continuous improvement protocols (mandatory)

1. **Issue ledger: `docs/ledger/`, one file per entry (`I-NNN.md`).** The moment a problem appears (failed command, failing test, wrong assumption, environment quirk, rejected push), add its entry: `uv run python scripts/ledger_new.py --title "…" --where "…"` writes the next id's file, every field `TODO`, status open (#122, W-38, W-41). When it is resolved, complete the entry: root cause, fix, sweep, guard, status. The docs check fails on a `TODO` left in a closed entry, and on an entry written into `docs/ISSUE_LEDGER.md`, which is only the ledger's front page. Never leave a problem out because it was small or quickly fixed. One exception (#122, W-18): a habit lapse the push-gate hook refused, with nothing getting through, is not a ledger entry. The hook logs it to `hook-refusals.log` (in `%LOCALAPPDATA%/SCIO`, or `~/.cache/scio` elsewhere), and the retrospective reports its count per rule. A second exception (#141): a slip caught within the same turn with no effect is counted, not ledgered. No effect means nothing committed, pushed, published or left changed. Count it with `uv run python scripts/slip.py "<kind>" "<what happened>"`; `scripts/metrics.py` reports the counts. A slip that got through, or that repeats, is a problem and gets its entry.
2. **Milestone retrospectives: `docs/LESSONS_LEARNED.md`.** Before starting a milestone, read this file end to end and say which lessons shape the plan. At the end of a milestone, add a section: what succeeded, what failed, actions taken (each action is a file change, a test, a rule, or a ledger id, not an intention).
3. **Systemic bug sweeps.** A bug fix has three parts: the root cause, a search of the whole codebase for the same construct (record the grep or pattern in the ledger entry), and a guard against recurrence (test, lint rule, docs check, or CONTRIBUTING rule). Fix every instance found. Do not patch only the file where the symptom showed.
4. **Always/Never guardrails, each with a guard that runs.** Every bug and every correction from the owner becomes one rule, its own file `docs/guardrails/NNN.md` (the next number from `scripts/next_ids.py`; #122, W-39). `## Guardrails (Always / Never)` at the top of `docs/LESSONS_LEARNED.md` says how they work. A rule starts with **Always** or **Never**, cites its id, and names its guard (`symbol:` a structural fix, `test:` a regression test or a scan, `check:` a docs check, `hook:` a Claude Code hook; `manual:` with the reason only when nothing can check it). `check_guardrails` fails when a resolved ledger entry from I-104 on has no rule, or a named guard does not exist. A rule without a guard is a wish. Read the active rules with `uv run python scripts/check_docs.py --active`. A quarterly review (#141; the first, 2026-11-15, left 21 of 100) merges related rules (`Status: merged into <n>`) and retires those a guard fully enforces (``Status: retired: `<guard>` enforces it``). Then `check_docs.py --write-active` sets the new cut-off in `docs/guardrails/ACTIVE.md`.
5. **Bottleneck audit after every pass** (a slice, a milestone, a live run): the slowest steps in minutes, work that ran one after another but could have run in parallel, friction that repeated, and 1 or 2 concrete improvements (a file change or a ledger id). It goes in the status report and the retrospective. It starts from the numbers: `uv run python scripts/metrics.py --write --product-root <the live workspace>` gives:
   - for SCIO PRs: lead time, gate and CI time, and the rework share;
   - for the live product: features per day, cost per feature, the escalation share, and the time stalled waiting on the owner.

## Workflow v2: the standing checklist (issue #122)

- **`docs/WORKFLOW_V2.md` is open work until every item is closed.** The `SessionStart` hook prints its count and next open items at the start of every session. Pick them up as you work, and never tick one by hand: `uv run python scripts/workflow_status.py` computes each item from its evidence in the tree, and the docs check fails on a malformed checklist.
- Write a problem's ledger entry before starting the gate that carries it: an entry added mid-gate kills the gate or forces a second run (W-01).
- Live status ("still running", "has not fired yet") goes in a PR comment, never in a gated file. A ledger entry holds settled facts (W-02).
- Read the workspace's own files (its launcher, RUN_LOG, open issues, the live run's state) before asking the owner anything they may already have answered (W-03).
- Ask for approvals once per batch, naming the issues or a `Refs #N` set, and record the owner's words with the PR or issue numbers in `.scio/approvals.md`. A merge needs a line there or the owner's own "merge N" (W-04).
- Inspection scripts live in scripts/dev/ or the scratchpad, written with the file tools, never inline in a heredoc or `python -c` (guardrail 17; W-05).
- Branch from main; stack a PR on another only when a conflict forces it, and then retarget it the moment its base merges (W-07).
- An agent reports open questions, never owner decisions. Every invariant the owner stated becomes a named acceptance test in the agent's brief (W-08).
- When a change depends on how a provider, the `claude` CLI or GitHub behaves, pair it with a research agent that checks the documentation or runs a probe, never memory (W-09). Brief it from `.claude/templates/research-brief.md`, whose first question is whether this repository can have the feature at all: its owner type, plan and visibility against the docs' availability line (I-227).
- Save each agent's final report to `.scio/agents/<issue>.md`; the PR body, the ledger entry and the review are built from that file, not from the conversation (W-34).
- Start a session with `uv run python scripts/session_state.py`: the pinned checkouts, every worktree, the PRs, the live-run issues, the recovery incidents, the next ids and the open checklist items, in one command. Take ledger ids and guardrail numbers from it (or `scripts/next_ids.py`), never from memory. The `Stop` hook writes the same facts to `.scio/session-state.md` for the handoff (W-20, W-21, W-28).
- Land a PR with `uv run python scripts/land.py N`. It retargets the PR, requires a gate stamp, watches CI by commit and marks the PR ready, but never updates the branch (#141). Once CI is green it prints the merge step, `land.py N --enqueue`, for three kinds of PR only:
  - an approved PR;
  - a revert of a PR that turned main red;
  - a low-risk PR that changes only docs or tests. It is labelled `low-risk`; `scio/`, scripts, hooks and CI stay the owner's to approve.

  After the merge, `land.py N --after-merge` waits for the queue to merge the PR, then watches main's own CI. A red main opens a `red-main` issue with the revert recipe. Move live-wt with `scripts/move_live_wt.py --when-idle`, never mid-build (W-22 to W-27).
- The repository is `CAIOT404/SCIO`, owned by an organization so that `main` can require a merge queue (#141; the old `NewMe505/SCIO` path redirects). A branch need not be up to date with `main`. `land.py N --enqueue` adds a green PR to the queue, and the queue merges it after its own `merge_group` CI run. So confirm `mergedAt` in a later step, never in the same command. Never `gh pr merge` here: it tries auto-merge, which this repository does not allow (I-233, guardrail 104). Never `--admin`, which bypasses the queue.

## Engineering rules

- Workflow and commits follow `CONTRIBUTING.md`: issue first, branch `feat/<issue#>-<slug>`, Conventional Commits, draft PR from the template with `Closes #N`, docs in the same PR, human merge.
- Run the gate before every push: `uv run python scripts/gate.py`.
  - By default it is quick: `ruff check`, `ruff format --check` and `mypy`, then the tests of the paths changed since the last pass. A shared fixture, a config, or a file no test names makes it run the whole suite.
  - The regression evals run only when `scio/`, `evals/`, `configs/` or `prompts/` changed. Then the docs check runs.
  - A change that is only Markdown docs runs only the docs steps.
  - `uv run python scripts/gate.py --full` runs what CI runs: `pytest -n 16` beside the regression evals (5 trials, `--min-pass-pow-k 1.0`). Use it for a release cut, after a red CI, and for a change to the gate or the push-gate hook.
  - A pass stamps its tree in `.scio/gate/last-pass.json`. The push-gate hook refuses to push a tree no pass stamped; `SCIO_ACK_GATE=<reason>` pushes anyway.
  - One gate runs at a time on the machine. A leftover `.scio/gate/RUNNING` means a gate died there.
  - The gate prints each step's time and the tail of a failed step's log (`.scio/gate/<stamp>/`), and exits 1 on any failure (issues #88 and #122). The tests run on 16 workers (the owner's decision, 2026-11-08, issue #88; 8 since #73, serial before). A test that fails only in parallel is rerun alone by its node id to tell a shared-state bug from a real one, and either way it gets a ledger entry. After a push, `uv run python scripts/watch_ci.py` waits for that head's own CI run (by SHA) and watches all its jobs: `gh pr checks --watch` can read the previous head's green checks (I-104). Always the `python -m` form for pytest, mypy and scio: Windows Application Control blocks the venv's `pytest.exe`, `scio.exe` and (since 2026-10-31) `mypy.exe` launchers on this machine (I-075, I-146), so `uv run python -m scio ...` as well. `ruff.exe` is ruff's own binary, not a launcher, and runs.
- Offline by default: `SCIO_PROVIDER_OVERRIDE=fake`. Live provider calls only in `tests/live` behind `SCIO_RUN_LIVE_TESTS=1`, or in explicit eval runs.
- Live credentials come from the `ant auth login` profile (the CLI is installed under `%LOCALAPPDATA%\Programs\ant`). The session may carry a stale placeholder `ANTHROPIC_API_KEY`; run live commands with `env -u ANTHROPIC_API_KEY -u SCIO_PROVIDER_OVERRIDE` so the profile wins. Live runs cost real money: run one trial first, report the cost, then scale. The profile's refresh token rotates: all providers share one SDK client per process (`shared_client`), and an `invalid_grant` error means the profile is dead and the user must run `ant auth login` again.
- Model IDs live only in `configs/models.yaml`. Code names roles. Check the Claude API reference (the `claude-api` skill) before writing any provider code; never write SDK calls from memory.
- Write files with LF line endings (`newline="\n"` in Python on Windows). Any text with a backslash (Windows paths, regexes, escapes) is written with the file tools, never through a shell-embedded script. Behind a corporate proxy, set `UV_SYSTEM_CERTS=1` for every `uv` command (`--native-tls` and `UV_NATIVE_TLS` are deprecated spellings).
- Parallel sessions follow the orchestration rules below. That is about how AI sessions build SCIO; the framework's own runtime keeps one writer per product (ARCHITECTURE.md), which these rules do not change.
- Tests, lint and types are ground truth. Do not weaken a check to make it pass; fix the code or record a ledger entry explaining the exception.

## Existing Codebase Parallel Orchestration Rules (15-Agent Pool)

- **State-First Inspection:** Before spawning agents, inspect the current file tree and state tracker. Never recreate existing modules or duplicate completed work. Here the state trackers are `git status`, the open PRs, the ledger's open entries (`docs/ledger/`), the milestone status in `docs/PRODUCT_MODE.md`, and the open `live-run` issues (`gh issue list --label live-run --state open`): a live product run's session opens one for each SCIO bug it finds, the moment it logs it (the owner's decision, 2026-11-05, issue #81). Each one gets a ledger entry when this session takes it up.
- **Concurrency Ceiling:** Dispatch up to **15 concurrent sub-agents** per execution wave for any tasks that do not share direct data or file dependencies.
- **Strict File Isolation (Anti-Collision):** In an existing codebase, every parallel sub-agent must be assigned an explicit list of `owned_files`. An agent may read any file in the repository for context, but may ONLY modify its assigned `owned_files`. Shared files (`docs/ISSUE_LEDGER.md`, `docs/LESSONS_LEARNED.md`, `CHANGELOG.md`, `README.md`, `pyproject.toml`, `uv.lock`) are owned by the orchestrator, which writes them after the wave from the agents' reports. The fragments are not shared: an agent writes its own ledger entries, rules and change notes, each its own file (`docs/ledger/I-NNN.md`, `docs/guardrails/NNN.md`, `changes/unreleased/`), at the ids its brief assigns (#122, W-38 to W-40).
- **Shared State & Contracts:** If multiple modules depend on a shared state machine, base class, or schema, update the shared contract FIRST in a single-agent step, then fan out up to 15 parallel sub-agents to update or build the downstream modules simultaneously.
- **Verification Gate:** After each parallel wave resolves, run syntax/import checks across all modified files before triggering the next wave (`uv run ruff check`, `uv run python -m mypy`, then the affected tests). Only the orchestrator runs git (stage, commit, push) and the full CI-equivalent before a push; sub-agents never commit.
