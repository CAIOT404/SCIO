A live `scio new` or `scio build` on the Claude Code backend (`SCIO_PROVIDER_OVERRIDE=claude_code`) checks the `claude` sign-in with one tool-less `claude -p --safe-mode` call before it writes anything (issue #103, `scio/harness/preflight.py`). A missing or expired sign-in is one line, `scio: sign-in required: <reason>. Run "claude auth login", then rerun.`, and exit 2, with no thread, checkpoint or product file left behind; a check that could not run (a timeout, no `claude` binary) is `scio: pre-flight check failed: <reason>; nothing was run.`, also exit 2. Before, the failure came at the first real model call, mid-milestone, as a harness stop on a thread already opened (I-249). The recovery supervisor reads the sign-in line as `external_auth` and escalates it with "Sign in again (`claude auth login`)", never a repair. The Fake provider and the API providers skip the check.
