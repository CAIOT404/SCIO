# ADR 0011: The milestone loop: the task graph as a subgraph, one thread per feature attempt, the orchestrator picks the work

- **Status:** Accepted
- **Date:** 2026-10-12
- **Milestone:** M8 Decompose + milestone loop (Product Mode, ADR 0007)

## Context
After M7 a repository exists with `PRODUCT.md` (features as black-box criteria, approved by a human) and `.scio/product/progress.json`. M8 turns the remaining features into merged milestones: group them, create the tracking issues, run each through the proven task graph, verify the integrated branch, open one PR per milestone for a human, and remember what happened so the next session continues from the repository alone. The M7 retrospective left one decision open: the planner's P1 (a walking skeleton with specific criteria) and the scaffold's skeleton are not the same thing, yet `progress.json` marked P1 done.

## Decision
1. **P1 is a feature run, not a scaffold side effect.** After bootstrap every feature in `progress.json` is `todo`, P1 included (`ProgressFile.initial`). The scaffold proves the toolchain; "done" means a feature run's own verify passed. The milestone planner's prompt says so, and the first milestone always starts at P1.
2. **A second graph, the same mechanics** (`scio/product/build.py`): `load -> plan_milestone -> issues -> feature* -> integrate -> milestone_gate -> [gate_decision] -> milestone_pr -> merge_wait -> update_progress -> plan_milestone | done` over `ProductBuildState`, compiled with the shared checkpointer, durability `sync`, thread `build-<product>` (one build thread per product; `scio build` resumes it until the product is done).
3. **The orchestrator picks the work; the planner proposes the grouping** (I-046). The next feature is always the first open one in `PRODUCT.md` order. The `milestone_planner` role (Opus, `MilestonePlanOutput`) proposes which open features form the milestone and a tier per feature; `normalise_milestone` keeps only a consecutive prefix starting at the first open feature, caps it at four, defaults tiers to T1 and records every change as a ledger note. The milestone branch is `milestone/<n>` from `main`.
4. **Tracking is idempotent by title.** With a GitHub client: `ensure_milestone("Mn: title")` and `ensure_issue("Pk: description", ...)` look up the title before creating, and each is wrapped in `run_effect` with a probe (`find_milestone`, `find_issue`). Amended 2026-11-04 (graphcalc S7): `find_issue` lists the repository's issues and matches the title exactly. It never searches, because a `"` in a title broke the search phrase (I-150). A milestone's identity is its id: its plan is committed on its branch (`.scio/product/milestones/Mn-plan.json`) and reused when a later thread plans it again, and its GitHub milestone is found by the `Mn: ` prefix, since a second planner call can retitle it (I-149). Offline: one Markdown file per feature under `.scio/product/issues/`, committed once on the milestone branch with a `[scio:issues:Mn]` marker.
5. **Each feature attempt is a task subgraph on its own thread.** `feature_context` derives a `RunContext` from the orchestrator's: the same sandbox (the product repository), effect log and prompts; a `Harness.child` with its own tier-pinned `BudgetGuard` and cost ledger; no GitHub client. The thread id is deterministic, `build-<product>-<pk>-a<attempt>`, so a crash mid-feature resumes the same subgraph (`thread_started` probes the checkpoint store); `run_graph`/`resume_graph` accept the orchestrator's open saver so both graphs share one store. The `TaskSpec` handed over carries the feature's criteria as acceptance, `milestone/<n>` as base branch, the issue number and the pinned tier. The task graph's `merge_wait` is answered by the orchestrator, which fast-forwards `milestone/<n>` to the feature branch (effect with an `is-ancestor` probe). Any other pause, or a non-success exit, becomes **one** product-level interrupt: `retry` (a new attempt, new thread; `retry: <answer>` carries the owner's answer into it, see the #137 amendment), `skip`, or stop (`feature_failed`). The subgraph's own interrupt is closed with the same answer. *Amended 2026-10-28 (I-116, the owner's decision):* `skip` defers the feature to the next milestone. A skipped feature stays open, the release refuses while any feature in PRODUCT.md is not done, and a feature leaves the product only when it is removed from PRODUCT.md.
6. **Ground truth outranks the gate.** `integrate` runs the profile's full suite and lint on the milestone branch; a failure halts with `integration_failed` before any model is asked. `milestone_gate` (Opus, `GateOutput`) sees the features, each run's outcome, the integration output and a diff stat; a `pass` verdict is overridden to `escalate_human` when the checks failed or a feature is not `passed`. A non-pass verdict on green checks is one human question (`proceed` or stop). *Amended 2026-11-15 (issue #140, I-230):* a feature the owner answered `skip` in this milestone is deferred, not undelivered. The gate's input lists it under "Deferred by the owner" without its criteria (prompt v2), and it never forces the override. A feature that failed, never ran or stopped without the owner's `skip` still does, and so does a milestone whose every feature was deferred (nothing was delivered).
7. **One PR per milestone, one human merge.** The PR body (cost per feature and for the orchestrator, escalations resolved/total, plan versus done, `Closes #n` per issue, the integration output, the gate verdict) is pushed with the branch and opened as a draft then marked ready; offline it is written to `.scio/product/milestones/Mn-pr.md`. `merge_wait` interrupts; `merged` with GitHub checks `pr_merged` and pulls `main` (asks again if the PR is still open); `merge` offline merges `--no-ff` with a `[scio:merge:Mn]` marker. `update_progress` records the milestone and its features (status, commit, thread, tier, issue, cost) in `progress.json`, prepends a line to `NOTES.md`, commits on `main` with `[scio:progress:Mn]`, and loops to the next milestone while features remain, unless the human answered `merge and stop`, in which case the thread ends after the record (the first live milestone needed a stop before the next one started spending). Threads are named per starting milestone, `build-<product>-m<n>`, and `scio build` starts a fresh thread (`-r2`, ...) when the one for the next milestone has already ended.
8. **Verify counts new files.** The first Fake build found that `git diff --stat <base>` ignores untracked files, so a feature delivered only by new files read as "no changes" (I-063). `diff_stat` now appends every untracked file and the full diff uses `git add -N` first.

## Consequences
- `tests/graph/test_product_build_fake.py` is the executable acceptance: a two-milestone Fake product (P1 at T0, P2 and P3 at T1) builds through the task graph with the product's own CI green on `main`; a crash at the gate of the second feature and a crash after the PR resume with no duplicated issue, commit, milestone or PR (offline files and a canned `gh` against a bare origin); a failing integration check or an unpassed feature overrides a passing gate verdict; an escalation inside P3 (repeated error, advisor, guided fix) is recorded on the product's `FeatureRun`, in the PR body and in the report; feature failures stop for one decision each (`skip`, `retry` on a new thread, stop); the milestone gate's escalation asks the human; the CLI (`scio build`, `scio status`, `scio report` on a `build-*` thread) works end to end.
- Costs: the orchestrator's own calls run under T1 caps as runaway guards; each feature under its tier's caps; the product has no cap (ADR 0007). `total_usd` (orchestrator plus every attempt) is in every interrupt payload and PR body.
- Open for M9: `integrate` runs tests and lint only; build, smoke against a running app, audit and the coverage floor arrive with the toolchain's runtime commands. The sandbox is still the local backend for product builds.
- Open: a feature that fails after a retry has no automatic path; the human decides each time. A `replan` verdict from the milestone gate is treated like `escalate_human` (one question) rather than re-running a feature.

## Amendment (2026-11-14, issue #119): a retry starts from the last verified commit
In the graphcalc run, P26 attempt 3 passed verify and `committed F1+F3 as 8b8e8b4`, then halted. The operator's `retry` started attempt 4 at the milestone head: every attempt of a feature uses the same `agent/...` branch, and `prepare_repo`'s `checkout -B` reset it, orphaning the commit. Attempt 4 spent 32 minutes rebuilding F1 and F3.

- **Only a retry carries.** `FeatureRun.decision` records the owner's answer (`retry`, `skip`, `stop`). `retried_runs` takes this milestone's runs of the feature that were answered `retry`, newest first, up to the first one that was not. A skip, a stop, a harness failure (no one was asked) or another milestone ends the chain, so those attempts start from the milestone head, as before.
- **The marker is the attempt's own state.** `verified_start` reads each retried attempt's checkpointed task state. A feature's `commit_sha` is set by `git_checkpoint` alone, and only after a passing verify with the whole suite green. The newest such commit, a descendant of the others, is the start. An attempt that committed nothing (it carried work and halted before its own checkpoint) passes the search on to the attempt before it.
- **What is carried.** Only features whose ids come from the acceptance criteria (`features_from_acceptance`), and only while the criteria are the ones the attempt built. A planner's own feature ids may mean something else next time.
- **The start must sit on the milestone head.** The milestone branch takes a feature by fast-forward (or the ADR 0018 merge) only once the whole feature has passed, so it never holds a half-done one. A head that moved since (a hand edit of `PRODUCT.md` committed at the stop, I-109) would make that fast-forward fail. Then the attempt starts from the head, and the ledger says why.
- **How it flows.** `TaskSpec.start_commit` and `TaskSpec.carried`. The orchestrator still cleans the tree first (I-067), so uncommitted leftovers are discarded. `prepare_repo` checks out the base branch, records its head as `base_sha`, and runs `checkout -B <branch> <start_commit>`. `base_sha` stays the milestone head, so verify's change check, the diff and the gate see the whole feature. `carry_features` marks the carried features passing with their test filter. Their `commit_sha` stays unset: the attempt's next checkpoint stamps them, which also advances a plan step that covers only carried features. The brief says the attempt continues from the commit.
- **The ledger.** The orchestrator writes `Pk attempt N starts from <sha> (F1, F3 verified in attempt N-1)`. A node run that pauses for a decision loses its facts, so the run that resumes the thread writes `Pk attempt N started from <sha> (... carried as passing)` from the thread's own task. The task ledger says `repository ready on branch ... at <sha>, on top of <head>; carried as passing: ...`.
- **Resume and parallel features.** A resumed thread keeps its task, so the start is never chosen again. `ready_batch` runs a feature that already ran in this milestone alone, so a retry always takes the serial path, and ADR 0018's batch path is unchanged. After a batch, the siblings' merges have usually moved the head, so the retry starts from the head, as ADR 0018 says.
- **Tests:** `tests/unit/test_retry_keeps_verified.py`.

## Amendment (2026-11-15, issue #137): the owner's answer reaches the retried attempt
In the graphcalc run, P29's T0 coder stopped with `design decision needed: ...` (two ways to make `1.2.3` an error; which one?). The feature stop offered `retry`, `skip` or stop. A `retry` built the next task from the spec loaded when the milestone started, so the owner's one-sentence answer had no way in: a hand edit of `PRODUCT.md` is committed at the stop but never reaches the task, and a `skip` reaches it only one milestone later. The owner approved: "The fix would carry 'retry <your answer>' into the next attempt's task, next to the question it answers."

- **The reply.** `retry: <answer>` (or `retry - <answer>`, `retry, <answer>`, `retry <answer>`): the text after the keyword, without its leading `:`, `-`, `,` and whitespace, is the answer, in the owner's case (`retry_answer`). The keyword matches in any case, as before, and counts only when the reply ends there or a separator follows. A plain `retry` answers nothing, and neither does `retrying please`, which is still a retry. The stop's question and its `resume` hint (`<retry[: your answer]|skip|stop>`) say so.
- **The question.** `stop_question` reads it from the attempt's own state, in this order:
  1. The worker's `design_question` (`last_worker_output`). On T1/T2 the advisor gets the question first, and no ledger line names it.
  2. The coder's `design decision needed: ...` line in the task ledger (T0), which the stop shows in its `ledger_tail`.
  3. The stop's own line, `Feature <id> (<reason>, attempt <n>)`, when the attempt asked nothing.

  The task graph's own interrupt asks only "The run needs a human decision.", so its `question` is not used. `stop_question` runs before the subgraph's interrupt is closed. A node run that resumes the stop re-runs the paused attempt first, so a stop reached before this change gets the answer through too.
- **The record.** `FeatureRun.question` and `FeatureRun.answer`, both optional and None by default, are set on the `retry` record only when it carries an answer, in full. A checkpoint written before them still loads. The 120-character human note is unchanged.
- **The task.** `feature_task(answers=...)` takes `(attempt, question, answer)` triples and appends them after the linked bug issue (#120), under `## The owner's answers to earlier attempts' questions`, oldest first, each as `Attempt <n>`, `Question:` and `Answer:`. `owner_answers` gives every answered `retry` of the feature in this milestone, from `state.feature_runs`, to both call sites (the serial feature and the ADR 0018 batch). Unlike `retried_runs`, a plain retry or a stop in between does not end the list, since an answer stays true. With no answers, the description is the one before this change, byte for byte. The #119 carry note still comes last.
- **Unchanged:** `skip`, stop, the #119 verified-commit carry, the #120 linked bug issue, the ledger notes, the dashboard and the report.
- **Tests:** `tests/unit/test_retry_answer.py`.
