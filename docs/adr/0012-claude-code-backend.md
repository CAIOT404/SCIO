# ADR 0012: The Claude Code backend: SCIO's model work through the unmodified `claude` binary on a Claude subscription

- **Status:** Accepted
- **Date:** 2026-10-12
- **Issue:** #47

## Context
Every SCIO run until now called the Messages API through the Anthropic SDK, authenticated by an `ant auth login` profile. That is Console API billing by the token, which the owner does not want: they hold a Claude Max subscription. Anthropic's terms (code.claude.com/docs/en/legal-and-compliance) allow a subscription login only inside the unmodified Claude Code binary, say that Pro and Max limits "assume ordinary, individual usage of Claude Code and the Agent SDK", and forbid routing requests through subscription credentials on behalf of other users or intermediating their tokens. A program that calls the API itself must use API keys. SCIO is such a program, so the only compliant way to run it on the subscription is to have the unmodified binary make the model calls, in print mode, signed in by the owner.

Facts checked before the design (pre-flight 8): `claude -p --output-format json` returns `result`, `session_id`, `usage`, `modelUsage` and `duration_api_ms`; `--json-schema` returns a `structured_output` that matches the schema; `--restricted --tools ""` removes every tool and ignores the user's settings files; `--max-turns`, `--max-budget-usd`, `--permission-mode acceptEdits`, `--permission-prompts none`, `--system-prompt-file` and `--resume <session>` exist; `--bare` does *not* use the subscription login, so it is never used; print mode refuses to start under `CLAUDECODE=1`, so that variable is stripped; a run inside this very Claude Code session worked once stripped.

## Decision
1. **Two seams, one setting each.** `SCIO_PROVIDER_OVERRIDE=claude_code` routes every tool-less role (router, planner, advisor, gate, reviewer, interviewer, product planner, milestone planner and gate) through `ClaudeCodeProvider`, a `ModelProvider` whose `complete` and `structured` each run one `claude -p` process: `--restricted --tools "" --max-turns 1 --no-session-persistence --model <role model> --system-prompt-file <static prompt> [--effort] [--json-schema <wire schema>]`, messages on stdin (a repair conversation is rendered with its roles). `SCIO_WORKER_BACKEND=claude_code` routes every tool-using turn (coder, debugger, documenter, explorer) through `ClaudeCodeWorker`, which has `AgentLoop`'s surface. The two can be combined (nothing touches the API) or used alone.
2. **A worker turn is one Claude Code session plus one resume.** `claude -p --output-format stream-json --verbose` runs in the sandbox root with the role's static prompt plus a note mapping SCIO's tool names to Claude Code's, the task projection on stdin, `--allowedTools` derived from the SCIO toolbox (Read, Glob, Grep for the read tools; Edit, Write, MultiEdit for `edit_file`; `Bash(<test runner> *)` and `Bash(<linter> *)` for `run_tests`), `--permission-mode acceptEdits --permission-prompts none`, `--max-turns` in Claude Code turns from `claude_code_max_turns` (T0's coder `T0_TURN_CAP` and the documenter's `DOCUMENTER_TURN_CAP`, both measured; amended 2026-11-04: SCIO's tool-call caps were passed as turns here, and a turn holds 1.6 tool calls, I-153), `--max-budget-usd` from the remaining budget and `--name scio-<role>`. The `stream-json` events are rendered into SCIO's transcript shape (`assistant: <tool_use name {...}>`, `tool_result: ...`), subagent traffic excluded, so `scio report`'s tool signals read it unchanged. Then one `--resume <session> --tools "" --max-turns 1 --json-schema <WorkerOutput>` call closes the turn with the typed output; an invalid reply is re-asked once with the validation error.
3. **Verify stays SCIO's ground truth.** Nothing in the Claude Code turn decides success: SCIO's `verify` runs the tests and lint afterwards exactly as before, `git_checkpoint` commits, the gate judges. What the backend loses is the ACI's per-edit lint gate and the sandbox's network and command limits inside the turn, because the binary runs on the host in the sandbox root; verify's lint catches what the edit gate would have.
4. **Cost is Claude Code's estimate, accounted like any call.** `Harness.account` records the usage of each `claude -p` run in the ledger and the budget at SCIO's prices (`modelUsage` names the model served), so budgets, caps and reports keep working; the dollars are what the API would have cost, nothing is billed. The provider's responses carry the session id as the request id.
5. **Boundaries.** Local sandbox only (Docker and E2B cannot run the host binary). The host's `~/.claude` settings and hooks load in worker turns (restricted mode skips them for tool-less calls). The `claude` binary and its login are the owner's; SCIO never reads, stores or forwards the credential. "Ordinary individual usage" is the owner's responsibility: SCIO's caps (iterations, stalls, turns, budget) bound each run, and nothing here serves other users.

## Consequences
- `tests/unit/test_claude_code_backend.py` (canned runner: argv shape, schema path, environment stripping, failure classification, transcript rendering, accounting, summary retry) and `tests/graph/test_claude_code_backend_t0.py` (t001 through the T0 graph with a canned actor that really edits the sandbox; verify on real pytest and ruff; two providers in one ledger) are the offline acceptance. One live t001 trial through the real binary on the owner's Max login is the live acceptance (LESSONS_LEARNED).
- Open: `--max-budget-usd` and SCIO's budget both bound a turn by the API-price estimate, not by subscription usage; when the subscription's usage window is exhausted Claude Code reports an error that SCIO classifies as fatal. A credential pre-flight (IDEAS_TRIAGE item 14) applies here too: a quick `claude -p` before the first turn.
- Open: the explorer and documenter prompts still name SCIO's tools; the backend note bridges them, a per-backend template variant would be cleaner once there is live data on how often the mapping confuses the model.

## Amendment (2026-11-14, issue #115): on the subscription the budget is a metric, not a stop
The owner, in the graphcalc run: "th budget is hypaathoical and should no halt scio. it is more of a metic im track and can use the info later to being optimize sico". On the subscription nothing is billed and the dollars are API-price estimates, so a cap on them stops real work to save money that is not spent.

- **Setting.** `SCIO_BUDGET_MODE` is `auto` (the default), `enforce` or `track`, read by `scio.harness.budget.budget_binding`. `enforce` binds the caps as before. `track` records them and never stops anything. `auto` tracks only when every call runs on the subscription (`SCIO_WORKER_BACKEND=claude_code` and `SCIO_PROVIDER_OVERRIDE=claude_code`) and enforces otherwise.
- **What a non-binding budget changes.** `BudgetGuard.reserve` never refuses a call, `BudgetGuard.exhausted` and the state's `Budget.exhausted` are never true (so no `budget` exit from `check_exit` or from a node's `BudgetExceeded` handler), and the worker passes no `--max-budget-usd`. This amends decision 2's "`--max-budget-usd` from the remaining budget" and decision 5's list of caps: on the subscription that flag is no longer passed, and the budget no longer bounds a run.
- **What stays.** The dollars and tokens are still recorded and shown in the ledger, `scio report` (its spend line reads "(tracked, no cap)"), `scio status`, the dashboard and each stop's `tokens ... usd ...` line, for tuning SCIO later. The iteration, stall, turn, tool and advisor caps and the recovery supervisor's hang timeout bound every run in every mode. `ClaudeCodeProvider` keeps its `error_max_budget_usd` handling: without the flag it cannot fire, and an `enforce` run still gets it.
- **Why an API key keeps its cap.** Any setup with a call off the subscription (the `aci` worker backend, or an API provider for the tool-less roles) bills real money per token, so `auto` keeps the caps binding there; the owner's words were about the subscription setup.

## Amendment (2026-11-18, issue #185): the summary resume keeps the session's tool list
Decision 2 closed a worker turn with `--resume <session> --tools "" --max-turns 1 --json-schema <WorkerOutput>` (three turns since I-077). Tool definitions are part of the cached prompt prefix, and both flags changed them: `--tools ""` removed the built-in tools, and `--json-schema` added a `StructuredOutput` tool. So every summary wrote the whole session to the cache again instead of reading it, about 15% of a feature's cost at API prices (I-250). This amends decision 2's closing call.

- **The call.** `claude -p --safe-mode --output-format json --resume <session> --model <role model> --max-turns 3 --permission-mode dontAsk --permission-prompts none` (`summary_argv`). It passes no `--tools`, no `--json-schema` and no `--allowedTools`.
- **Why the mode is passed.** A `-p --resume` starts in the settings' `permissions.defaultMode`. On the owner's machine that is `auto`, and there a probe's Write ran. Under `dontAsk` the same Write was denied. Reads inside the working directory still run.
- **The schema.** It travels at the end of the prompt, after "Reply with only one JSON object that matches this JSON Schema, with no prose and no code fence:". SCIO strips one code fence from `result`, parses it and validates it (`validate_with_trimming`). An invalid reply is asked again once, with the error, as before.
- **Measured** (Claude Code 2.1.327, claude-sonnet-5, one session). A plain summary on this argv, before the mode flag was added, read 28,144 cached tokens and wrote 1,078, where the old argv read none and wrote 12,790. The final argv, told to Write first, read 62,698 and wrote 1,452 over its 3 turns, and the Write was denied.
