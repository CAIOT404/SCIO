### I-228 · An owner's answer to a coder's design question never reached the retried attempt
- Found: 2026-11-15 · graphcalc M4 (live run) · scio/product/build.py _feature_decision
- Symptom: graphcalc P29 ("`.5` and `5.` accepted, as on a TI", T0, thread `build-graphcalc-m4-p29-a1`) halted `escalate_human` after 4 minutes. Its coder asked `design decision needed: ... "1.2.3" tokenizes as "1.2" immediately followed by ".3" ... (A) ... (B) ... Which approach should I implement ...?` The stop offered only `retry`, `skip` or stop (issue #137).
- Root cause: `_feature_decision` read only the keyword of the reply, and `feature_task` built the next attempt's task from the spec loaded when the milestone started. Nothing carried the owner's words into it. A hand edit of PRODUCT.md is committed at the stop but never reaches the task, and a `skip` reaches it one milestone later. The task graph's own interrupt asks only "The run needs a human decision."; the coder's question sits in the task ledger, shown as the stop's `ledger_tail`.
- Fix:
  - `retry_answer`: the text after `retry`, without leading `:`, `-`, `,` and whitespace, is the owner's answer, in the owner's case. The keyword counts only when the reply ends there or a separator follows. A plain `retry` has no answer, and neither has `retrying please`, which stays a retry as before.
  - `stop_question` is read before the subgraph's interrupt is closed. It takes the worker's own `design_question` when set (on T1/T2 the advisor gets the question first and no ledger line names it). Otherwise it takes the coder's `design decision needed: ...` line from the attempt's task ledger (T0). The stop's own line `Feature <id> (<reason>, attempt <n>)` is the last resort.
  - `FeatureRun.question` and `FeatureRun.answer` (optional, None by default) are set on the `retry` record only when it carries an answer.
  - `feature_task(answers=...)` appends `(attempt, question, answer)` under `## The owner's answers to earlier attempts' questions`, oldest first. `owner_answers` passes every answered retry of the feature in this milestone at both call sites (serial and batch). With none, the description is byte for byte as before.
  - The stop's question and its `resume` hint (`<retry[: your answer]|skip|stop>`) say how to answer. The ADR 0011 amendment.
- Sweep: `grep -rnE 'startswith\("retry"\)|feature_task\(|<retry|reply .retry' scio recovery scripts tests`. `_feature_decision` is the only reader of a `retry` reply. `feature_task` has two call sites, the serial feature and the ADR 0018 batch, and both pass the answers. Only `build.py` held the `<retry|skip|stop>` hint. The dashboard and the outcome file show `resume` as text and never parse it. `recovery/` never answers `retry`. No test pinned the old wording beyond `'skip' to defer it` and `remove it from PRODUCT.md`, which stay.
- Guard: the 7 tests in `tests/unit/test_retry_answer.py`. They include `test_a_retry_with_an_answer_carries_it_and_the_question_into_the_next_task`, `test_a_plain_retry_builds_the_same_task_as_before`, `test_every_answered_retry_of_a_feature_reaches_its_later_attempts`, `test_a_feature_run_recorded_before_the_answer_fields_still_loads` and `test_a_t1_design_question_is_carried_from_the_worker_output`. All 7 fail on the old code. Guardrail 101.
