### I-158 · A bookkeeping commit failed when `git status` listed a file whose content had not changed
- Found: 2026-11-04 · issue #79, the full product-build Fake suite after the I-149 change · `test_a_provider_failure_inside_a_feature_ends_the_build_gracefully`
- Symptom: `RuntimeError: git commit -q -m chore: record the M1 plan [scio:plan:M1:plan_milestone] failed: ... no changes added to commit`, in the second build thread, which reused M1's stored plan and wrote the same plan file again
- Root cause: `_commit_changed` committed whatever `git status --porcelain` listed. After the identical rewrite, status listed the plan file as modified, `git add` staged nothing, and `git commit` failed the node. Why status listed an unchanged file was not verified (LF writes, no `.gitattributes`; a stat-only change is the likely reading). The same helper makes the install, progress-sync and PRODUCT.md-edit commits.
- Fix: `_commit_changed` commits only when `git diff --cached --name-only -- <files>` is not empty, and returns None otherwise; `_start_milestone` writes the plan file only when its text differs
- Sweep: every SCIO commit made from a status listing (`grep -n "status\", \"--porcelain" scio/product/build.py`): `_commit_changed` (fixed; its three other callers inherit the check); the offline issues commit and `update_progress` already commit only when `status --porcelain` of their paths is not empty after `add`
- Guard: `test_a_provider_failure_inside_a_feature_ends_the_build_gracefully` (failed on the I-149 change before this fix), `test_a_milestone_planned_again_reuses_its_plan_github_milestone_and_issues`; guardrail 55
- Resolved: 2026-11-04 · Status: resolved
