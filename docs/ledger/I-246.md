### I-246 · A supervised build belonged to the session that started it: it died with that session, and the session could not be closed
- Found: 2026-11-17 · the workflow audit of the graphcalc live run (`.scio/agents/audit-D.md`, stop 28; RUN_LOG S18 notes) · issue #175
- Symptom: two things, one cause.
  - On 2026-11-15 21:36 UTC graphcalc's M6 run died with its operator session (Claude Code's low-memory reaper). The supervisor found the orphan at 00:55 UTC: 200 minutes stopped.
  - On 2026-11-17 a forked background session (`4b74e6ab`) was the parent of the M8 and then the M9 build (`python -m recovery run` <- bash <- `claude.exe --session-id 4b74e6ab`). The owner could not close that session without killing the build, and it kept acting at stops beside the session the owner was using: a duplicate retry refused by the lease at 16:15:37 UTC, a duplicate merge-queue enqueue, and merge stop 8 run by the session the owner had asked to stop.
- Root cause: `python -m recovery run` supervises the build as its own child and stays in the foreground until the build ends, so the only way to start one was as a child (a background task) of an operator session. A tick and a replay already started detached (`procs.spawn_detached`, `runner.start_replay`); the operator's own `run` had no such start, and there was no way to wait for a run's stop except to be the process that started it.
- Fix: `recovery/cli.py` and `recovery/runner.py`.
  - `run --detach` refuses a busy workspace with the attached run's line and exit 2, makes the run id (`runner.new_run_id`), and starts the ordinary supervised run through `procs.spawn_detached` (`runner.start_detached`: `cwd` the package root and `SCIO_RECOVERY_HOME` set, as `start_replay` does), passing the id as `--run-id`. It waits at most 10 s for the supervisor's run record, prints `recovery run: detached run <run id> (pid <pid>); stdout: <path>` and returns 0. The detached supervisor holds the lease, the stay-awake request and the hang watch.
  - `wait --workspace W [--run ID] [--tail N]` polls the store until the run is no longer running and its supervisor is gone, prints the tail of `stdout.log` and the incident line, and exits with the run's code (2 refused, 1 no exit code). It takes no lease and writes nothing.
  - `runner.supervise` takes an optional `run_id`; without it, and without `--detach`, an attached run is as it was. No store schema change.
- Sweep: `grep -rn "spawn_detached" recovery scripts`: the tick (`cli._start_tick`), the replay (`runner.start_replay`) and now `runner.start_detached`; no other process the supervisor starts is meant to outlive its caller. `grep -rn "supervise(" recovery scripts`: one caller, `cli._run`. `grep -rn "recovery run" docs scripts .claude`: `docs/RECOVERY.md` (updated); the live workspace's own launcher notes are outside this repository.
- Guard: `test_run_detach_starts_the_supervised_run_detached_and_returns_at_once`, `test_run_detach_prints_the_run_id_and_log_path`, `test_run_detach_refuses_a_busy_workspace_like_an_attached_run`, `test_an_attached_run_is_unchanged_by_the_detach_flag`, `test_wait_returns_the_runs_exit_code_and_stdout_tail`, `test_wait_takes_no_lease_and_writes_nothing` and `test_a_detached_run_outlives_its_starter_and_wait_reports_it` (`tests/recovery/test_detached_run.py`).
