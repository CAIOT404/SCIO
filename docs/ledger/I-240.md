### I-240 · A machine sleep was read as a hung build: the run was killed and a repair started
- Found: 2026-11-17 · issue #158 · recovery hang detection; run-20261116005554-052972, incident inc-20261117054801-f1e361, issue #158
- Symptom: run `run-20261116005554-052972` (graphcalc, `scio build`, M6) started 2026-11-16 00:55:54 UTC. Windows logged the machine entering sleep (Kernel-Power 42) at 00:55:56 UTC and waking (Power-Troubleshooter 1) at 2026-11-17 05:47:49 UTC; the scheduled task "SCIO recovery tick" shows 173 missed runs. At 05:48:01 the run was recorded `killed_hang`, incident `inc-20261117054801-f1e361` (class `hang`) opened issue #158, and a repair session started on a build that had run for 2 seconds. The orchestrator held the incident.
- Root cause: the hang check in the supervising parent's poll loop (`recovery/runner.py`, `_supervise_child`) compared wall-clock time: `clock() - max(run.last_progress_at, run.started_at) > limits.hang_after_s` (2700 s). A sleeping machine schedules neither the supervisor nor its child, so the first poll after the wake saw 29 hours "without progress". Nothing told time the supervisor observed from time the machine was down, and nothing asked Windows to stay awake while a build ran.
- Fix: the poll loop reads the clock once per iteration. Two consecutive readings more than `sleep_gap_s(poll_s)` apart (`SLEEP_GAP_S` = 300 s, or 4 poll waits when that is longer) are machine downtime: the gap is added to the run's new `downtime_s`, one note "machine was down <n> h; not counted as idle" goes in the run's new `notes`, and `idle_s` leaves out the part of each gap that lies after the last progress. A gap before the last progress excuses nothing, so a hang after a sleep is still killed after `hang_after_s` of awake time. Both fields are optional on `RunRecord`: an old record loads with 0.0 and no notes. `supervise` holds `stay_awake` around the child: `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` from the polling thread before the spawn, `ES_CONTINUOUS` alone in a `finally`; a no-op off Windows, and a failed call prints one stderr line and never stops the run. `python -m recovery status` shows `downtime` when it is not zero. `docs/RECOVERY.md` says so. The tick's orphan path is unchanged: a sleep suspends the supervisor and its child and kills neither, so `find_orphans` (both processes gone) cannot be reached by a sleep alone; a machine that lost power while asleep leaves an orphan, which `_on_classified` already replays with no issue and no repair.
- Sweep: `grep -rn "hang_after_s\|last_progress_at\|clock() -\|deps.clock() -" recovery/ scio/dashboard/supervisor.py`. The poll loop held the only idle-time comparison. `machine.py`'s `deps.clock() - started < LOST_REPLAY_AFTER_S` and `clock() - at` (backoff and lost-replay waits) only wait longer after a sleep, and a wait that ends during a sleep is due at the wake, which is what they mean. `brief.py` prints `last_progress_at` and compares nothing. `scio/dashboard/supervisor.py` reads the run record and compares nothing.
- Guard: `tests/recovery/test_sleep.py`: `test_a_sleep_gap_is_not_counted_as_a_hang`, `test_a_hang_after_a_sleep_is_killed_after_hang_after_s_of_awake_time`, `test_two_sleeps_are_both_excused_and_each_is_noted`, `test_a_supervised_run_asks_windows_to_stay_awake`, `test_the_stay_awake_request_is_released_when_the_child_raises`, `test_a_refused_stay_awake_request_never_stops_the_run` and `test_a_run_record_without_downtime_still_loads`, each seen failing on the old code; `test_a_real_hang_with_the_loop_running_is_still_killed` pins the behaviour that did not change.
