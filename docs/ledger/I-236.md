### I-236 · A retried attempt that carries every feature passes with an idle coder, so idle cannot stand in for its stop
- Found: 2026-11-15 · issue #141 part 5 (ADR 0020) · tests/unit/test_retry_keeps_verified.py
- Symptom: since a design question now parks the feature (I-235), `test_an_attempt_that_halts_before_its_checkpoint_passes_the_verified_commit_on` could no longer reach a stop on attempt 2 with the `design` mode. Swapping attempt 2 to `idle` failed with `KeyError: 'thread'`: there was no stop, and the build went on to `merge_wait`.
- Root cause: a wrong assumption that an idle coder always stalls. Attempt 2 carries F1 and F2 as passing (#119), and they are all of P1's features. An idle coder changes nothing, verify finds everything passing, and the gate passes. `idle` stalls only when a feature is still to build, as on a first attempt (`test_a_plain_retry_builds_the_same_task_as_before` uses it there).
- Fix: attempt 2 keeps `design` and follows the new path. The test runs in GitHub mode, so the question is a comment and no bookkeeping commit moves the milestone head. The answer is already in the workspace, so the next pass gives P1 attempt 3, which still starts from attempt 1's commit.
- Sweep: `grep -rn '"idle"' tests/unit tests/graph`. The other idle attempts are first attempts, or retries of attempts that committed nothing, so they stall as intended. The new and changed tests that use `idle` (`test_a_failure_without_a_question_still_stops_for_a_decision`, `test_a_plain_retry_builds_the_same_task_as_before`, the `stall-exit` case) assert the stop they expect.
- Guard: the test asserts that attempt 2 parked with no commit, and that attempt 3 starts from attempt 1's commit. A mode that passes instead fails both. Guardrail 108.
