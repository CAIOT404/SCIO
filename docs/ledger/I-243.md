### I-243 · land.py --after-merge failed its pull: two git commands ran in the main checkout at once
- Found: 2026-11-17 · the SCIO session · scripts/land.py (--after-merge), the main checkout
- Symptom: `land.py 170 --after-merge` saw the merge (16:29:57 UTC, `4142132`) and then exited 1 on `git pull --ff-only` (exit 128): "warning: fetch updated the current branch head", then "Your local changes to the following files would be overwritten by merge" for every file of PR #170, and "Cannot fast-forward your working tree". Seconds later the main checkout was clean and at `4142132`. Nothing was lost, but the watch of main's own CI never started, so it was started by hand (`watch_ci.py --sha 4142132 --branch main`).
- Root cause: two sessions each ran `land.py 170 --after-merge` against the one main checkout: the session the owner was using (16:22:23 UTC) and the forked background session `4b74e6ab` that then owned the graphcalc build (16:22:35 UTC; I-246). Their transcripts show both. Both waited for the queue, saw the merge at once and pulled at once. git's "fetch updated the current branch head" means `main` moved while this pull was still in its fetch: the other pull had moved it and was writing the working tree, so this pull's fast-forward found PR #170's files already changed. The other run pulled, watched main's CI and passed. `land.py` wrote the main checkout with no lock, and nothing else stops two writers on one checkout. The I-246 fix (a build no session owns) removed this occasion, but any two sessions landing PRs close together could still race.
- Fix: `scripts/session_state.py` `checkout_lock(checkout)`, a context manager on the gate's machine-wide lock (W-16) in another file, `checkout.lock` beside `gate.lock`. It is created atomically with the holder's pid and checkout, and taken over when its process is gone. `land.py --after-merge` pulls the main checkout inside it, and `move_live_wt.py` moves live-wt inside it. A second writer prints `checkout: waiting for the checkout in <path> (pid N, since T)`, then finds nothing left to do. `gate.acquire_lock` takes a `name` for its messages; the gate's own messages are unchanged.
- Sweep: `grep -rn '"pull"\|"checkout"\|"merge", "--ff' scripts recovery --include=*.py`:
  - `scripts/land.py:677` (the pull, fixed);
  - `scripts/move_live_wt.py:88` (live-wt's checkout, fixed);
  - `recovery/runtime.py:203,219,233` (the supervisor's live-wt moves). These are not changed: the supervisor uses the standard library only and never imports `scripts/`; it moves live-wt only under its own lease, during an incident; and `move_live_wt.py` moves only when the supervisor shows no run and no open incident.
  - `scripts/hooks/push_gate.py` only reads command lines.
