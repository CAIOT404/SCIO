### I-147 · An existing product's PRODUCT.md could hold at most 24 features
- Found: 2026-11-04 · issue #77, the graphcalc live run's S10 (merge stop 2, thread `build-graphcalc-m2`) · parsing the edited PRODUCT.md with the pinned SCIO
- Symptom: `pydantic_core._pydantic_core.ValidationError: 1 validation error for ProductSpec` / `features  List should have at most 24 items after validation, not 26 [type=too_long]`, after the owner added the bug-fix and revision features P23 to P26 to the approved 22
- Root cause: `ProductSpec.features` carried the interview draft's bound (`max_length=24`, the same as `ProductSpecOutput` since M7), but `ProductSpec` is what every later run parses PRODUCT.md into. The bug workflow ("fix it through SCIO: add a feature to PRODUCT.md") grows that file for the product's whole life, so a product near 24 features could not take a fix. No test parsed a spec over 24.
- Fix: `ProductSpec.features` has no upper bound; `ProductSpecOutput` keeps 24, so a first spec stays small. graphcalc's edited PRODUCT.md parses with the fix (26 features, P23 to P26 after P4), and its paused `build-graphcalc-m2` checkpoint loads under the new models (checked on a copy of the checkpoint DB).
- Sweep: `grep -n "max_length" scio/state/models.py` over the models PRODUCT.md is parsed into (`ProductSpec`, `ProductFeature`, `AppSpec`): `features` (lifted); `users` (6) and `quality_bar` (12), kept: the bug workflow does not grow them, and a breach is now refused out loud at the merge stop (I-148); `ProductFeature.description` (400), kept: graphcalc's longest is P5's 349 characters, and GitHub took that issue title (#8, #12). `grep -rn "max_length=24\|at most 24" scio tests docs`: only the draft bound. `grep -rn "parse_product_md(" scio evals`: every reader (the CLI, `load`, the re-read, `scio new --spec`, `scio upgrade`, the product eval solver) builds `ProductSpec`, none the draft model.
