### I-249 · A live product command found an expired claude sign-in only mid-milestone
- Found: 2026-11-18 · Product Mode (#103) · scio/cli.py new and build on the Claude Code backend
- Symptom: a live `scio new` or `scio build` on the Claude Code backend learned that the `claude` sign-in was missing or expired only at its first real model call, inside the graph, after it had named and opened a thread. It ended as a harness stop (`scio build stopped on a harness error: FatalError: claude -p failed: Not logged in · Please run /login`) with a checkpointed thread to resume, in the middle of a milestone. I-060 (the API profile's `invalid_grant`) and I-064 were the same failure on the other credential; I-061 left an empty checkpoint behind.
- Root cause: nothing checked the credential before the command started work. The first call that could fail on it was whichever role ran first (the interviewer for `new`, the milestone planner for `build`), and by then the CLI had created the run context, the checkpoint store and the thread. The supervisor read the stop through its `not logged in` marker only when `claude`'s own words carried one.
- Fix: `scio/harness/preflight.py`, new: `check_sign_in(runner)` makes one `claude -p --safe-mode --output-format json --restricted --tools "" --max-turns 1 --no-session-persistence` call with "Reply with OK." on stdin, 60 s timeout, through the injectable runner. It names no `--model`, as the probe ran it: the router role's cheaper model has never run through `claude -p` (the graphcalc ledgers hold Opus and Sonnet calls only), and a model the sign-in could not use would refuse every live command. The signed-out answer the probe saw (exit 1, `is_error: true`, `result: "Not logged in · Please run /login"`), or any answer naming a sign-in marker, raises `SignInRequired`. A timeout, a `claude` that cannot start, any other error result or a non-JSON answer raises `PreflightFailed`. Text on stderr after a good answer comes back as a warning. `scio/cli.py`: `_preflight` runs it in `new` (after the argument refusals, before the thread is named and before a resume reads the checkpoint store) and in `build` (after the `progress.json` refusal, before any thread is named or opened, so a `--decision` resume too), only when `SCIO_PROVIDER_OVERRIDE=claude_code`. A refusal is one line on stderr and exit 2 through `_Outcome.refuse` (`scio: sign-in required: <reason>. Run "claude auth login", then rerun.`, or `scio: pre-flight check failed: <reason>; nothing was run.`), with the outcome file's `status` `refused` and `thread` null. `recovery/classify.py`: `scio: sign-in required:` is the first of `AUTH_MARKERS`, so every pre-flight refusal is `external_auth` under one signature whatever reason it quotes. `recovery/machine.py`: the `external_auth` escalation names `claude auth login`.
- Sweep: `grep -rn "RunContext.create(" scio`: three sites in `scio/cli.py`, `_new` and `_build` (both now behind the pre-flight) and `_task` (`scio run`, `scio resume`), which #103 leaves out: it is task mode, not a live product command (reported as an open question). `grep -rln "claude_runner\|ClaudeCodeProvider\|ClaudeCodeWorker" scio recovery scripts evals`: the provider, the worker and `scripts/dev/claude_probe.py` all start `claude` only after a command has passed its entry point; the recovery repair session (`recovery/repair.py`) is never started for `external_auth`. `grep -rn "Sign in again" recovery tests`: the replay branch of `_replay_finished` quotes the classification summary, which already carries the pre-flight's `claude auth login`.
- Guard: `test_a_live_build_runs_the_preflight_before_any_model_call`, `test_a_signin_failure_exits_2_with_the_instruction_and_no_state`, `test_the_fake_provider_skips_the_preflight` and `test_the_supervisor_reads_the_outcome_scio_writes_for_each_preflight_refusal` (`tests/unit/test_preflight.py`); `test_a_preflight_refusal_is_external_auth_and_never_repaired` (`tests/recovery/test_preflight_classify.py`).
