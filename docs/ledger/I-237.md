### I-237 · Releasing a held incident after newer merges would move live-wt backwards to the repair's merge commit
- Found: 2026-11-15 · issue #141 · recovery/machine.py _on_awaiting_merge / runtime.move_live_wt; incident inc-20261115035430-4fad71 (held)
- Symptom: found by reading the code, nothing was harmed. graphcalc's incident `inc-20261115035430-4fad71` (issue #142) is held on the owner's word; its repair PR #144 merged as `5e31305`, and `main` has since taken #146 to #152. The plan is to move live-wt to `main`'s tip with `scripts/move_live_wt.py --when-idle`, then release the hold. On release, the awaiting-merge step would call `runtime.move_live_wt(cfg, <merge SHA>)`, which refuses only a target that is not an ancestor of `origin/main`, so live-wt would go from the newer tip back to `5e31305` and graphcalc would resume without #140's fix or the question channel. Then `lock_changed(<tip>, 5e31305)` would blame any `uv.lock` change made on `main` after the repair on the repair, roll back and escalate.
- Root cause: the step took the repair's merge commit as the only possible target. It never asked whether live-wt was already past it, and the lock check compared with the merge SHA, not with the commit the resume runs on. The rollback point is also kept in the step log, so a move that waited on a running SCIO keeps the HEAD from before the owner's move.
- Fix: `runtime.contains(path, sha)` answers `git -C <live_wt> merge-base --is-ancestor <sha> HEAD`. A commit live-wt has not fetched answers False, not exit 128, and a git failure raises. `machine._on_awaiting_merge` reads `_effective_target` fresh on every tick, never from the step log. When HEAD is not the merge SHA but contains it, live-wt is not moved, the timeline says "live-wt at <head> already contains the fix <sha>; not moved", and that HEAD becomes the rollback point. Otherwise it moves to the merge SHA as before, with the same CI, `scio_running` and rollback rules; a HEAD equal to the merge SHA keeps the run's SHA as its rollback point. A new optional field, `Incident.live_wt_target`, records the effective target: the move step's probe and `_health`'s `lock_changed(prev, target)` use it. An incident recorded before this change has it empty and compares with `merge_sha`, as it did. `docs/RECOVERY.md` step 4 says so.
- Sweep: `grep -rn "move_live_wt\|merge_sha\|prev_live_wt\|lock_changed\|checkout --detach" recovery/ scripts/`. The only other live-wt move is the owner's `scripts/move_live_wt.py`, which checks out `origin/main`'s tip, so it cannot go backwards. `rollback_live_wt` goes to the recorded rollback point, which is that HEAD when live-wt was not moved. `merge_sha` keeps its meaning, the repair's merge, for the recurrence check (`machine.py`) and the brief's history (`brief.py`).
- Guard: `tests/recovery/test_machine.py`: `test_a_live_wt_that_already_contains_the_fix_is_not_moved_back` and `test_a_live_wt_moved_past_the_fix_while_the_move_waited_is_not_moved_back` (invariant 1), `test_a_live_wt_behind_the_fix_still_moves_to_the_merge_sha` (2), `test_a_lock_change_after_the_fix_is_not_blamed_on_the_repair` (3), each seen failing on the old code. Also the rollback and the old-incident tests there, and `contains` on real git in `tests/recovery/test_runtime_live_wt.py`. Guardrail 110.
