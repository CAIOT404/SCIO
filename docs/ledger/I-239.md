### I-239 · The supervisor's hang limit counted a machine sleep: a healthy build was killed as hung on wake (#158)
- Found: 2026-11-17 · issue #158, recovery incident `inc-20261117054801-f1e361` · recovery/runner.py _supervise_child (hang check)
- Symptom: graphcalc's replay `run-20261116005554-052972` (SCIO 2d768c7) resumed the orphaned `run-20261115205736-514a5e`: build thread `build-graphcalc-m4`, M6, P10 attempt 1. It started 2026-11-16 00:55:54 UTC, made its last progress at 00:55:55, and the supervisor killed it as hung at 2026-11-17 05:48:01. The limit, `hang_after_s` = 2700 s, should have fired at about 01:41, but the kill came 28 h 52 min after the last progress. The run's stderr held only the two `LocalSandbox cannot disable the network` lines, its stdout was empty, and it wrote no checkpoint. The incident was classified `hang` and a repair started. The machine was asleep for nearly all of that time. Per-minute counts of file writes under `%LOCALAPPDATA%`, `%APPDATA%`, `~/.claude` and the workspace `graphcalc-run` show:
  - none from 00:56 UTC on 11-16 to 05:47 UTC on 11-17, except 11 at 08:50 (a Chrome extension update) and 4 at 10:39 (Chrome's CRL set);
  - the wake at 05:47, with 685 files written;
  - the kill at 05:48:01, the supervisor's first poll after the wake.

  The 08:50 and 10:39 writes came from short maintenance wakes in which the supervisor did not poll: the old check would have killed the run at 08:50. The same suspend shows in the orphaned run's P10 worker transcript. After `ENOTFOUND api.anthropic.com` (the network drops as standby starts), it scheduled a 9.4 s retry at 2026-11-15 21:54:04, and that retry fired at 2026-11-16 00:40:32. So the child had about a minute awake after its last write, never 45 minutes. Nothing shows a stall in SCIO's build itself: this fix does not touch the build.
- Root cause: `_supervise_child` decided a hang by `clock() - max(run.last_progress_at, run.started_at) > limits.hang_after_s`, with `clock` = `time.time`. That is the wall clock, which counts the hours a laptop sleeps, when neither SCIO nor the supervisor can run. So the first poll after any sleep longer than 45 minutes killed whatever run was in flight, opened an incident and started a paid repair session.
- Fix: `recovery.runner.Silence` counts the supervisor's own awake time with no progress:
  - Each poll adds the gap since the poll before.
  - A gap more than `SUSPEND_GAP_S` (60 s, an absolute margin so a slow poll on a loaded machine never looks like a sleep) over `poll_s` adds `poll_s` only. The rest goes to `slept_s`.
  - Progress resets the count to zero, and the hang check is `quiet > hang_after_s`.

  It reads only the gaps between polls, so it does not depend on whether a clock runs on through a suspend (`time.monotonic` on Windows differs by Python version). With `echo` on, the supervisor prints the slept seconds to its own stderr, never to the run's `stdout.log` or `stderr.log`, whose modification times count as progress. Behaviour without a sleep is unchanged. `Limits.hang_after_s`'s docstring, ADR 0019's failure-class table and `docs/RECOVERY.md`'s `recovery.toml` example now say "awake time". The fix is on branch `fix/158-recovery-5681b8`, in the PR that closes #158.
- Sweep: `grep -rn "time\.time() *-\|clock() *-\|monotonic() *-\|deadline" --include=*.py scio recovery scripts` and `grep -rniw "hang\|hung\|stalled\|stale" --include=*.py scio recovery scripts`. The construct is an in-process watchdog that judges silence from elapsed time across its own polls. There is one instance, `recovery/runner.py`'s hang check, now fixed. These were reviewed and are not instances:
  - `recovery/machine.py`'s `LOST_REPLAY_AFTER_S` (900 s). It is a wall-clock check made across ticks, not polls. It can misfire only if a sleep lands in the second between a replay's start and its first run record. A fix needs the replay's process key, which its step does not store. It is left as it is and named as a risk on the PR.
  - The total-duration caps on `time.monotonic` through `subprocess` timeouts: `scio/proctree.py`'s `run_tree` (the Claude Code worker's 1800 s turn), sandbox `exec` timeouts and `gh` timeouts. These are caps, not no-progress watchdogs. Whether they count a suspend on Windows is unverified, and that is named as a risk.
  - `scripts/watch_ci.py`, `scio/product/pr_ci.py`, `scripts/move_live_wt.py` and the supervisor's `ci_wait_s`. They wait on GitHub CI or on processes that keep running while the laptop sleeps, so the wall clock is right for them.
  - `scripts/gate.py`'s `UNWRITTEN_LOCK_STALE_S` covers a lock left empty for a minute. Its window is microseconds between `O_CREAT` and the write.
- Guard: these tests in `tests/recovery/test_runner.py`:
  - `test_a_machine_sleep_never_counts_toward_the_hang_limit`: a stub child silent for 1.5 s across an injected wall-clock jump of the incident's 103 926 s, under the default 2700 s limit. On the old code it ended `killed_hang` with exit 1, the incident's own outcome. Now it ends `exited` with 0.
  - `test_a_child_silent_after_a_machine_sleep_is_still_killed_after_hang_after_s_awake`: a silent child is still killed, after `hang_after_s` of awake time. On the old code the kill came 0.56 s after the wake with a 1.5 s limit.
  - `test_a_machine_sleep_is_reported_on_the_supervisors_stderr_never_in_the_runs_logs`.
  - `test_silence_counts_each_poll_gap_and_a_sleep_as_one_poll`.
