### I-227 · GitHub refused the merge-queue rule on the protect-main ruleset
- Found: 2026-11-15 · Workflow v2 (#122, W-44) · `gh api -X PUT repos/NewMe505/SCIO/rulesets/24860698` with the existing rules plus a `merge_queue` rule
- Symptom: `{"message":"Validation Failed","errors":["Invalid rule 'merge_queue': "],"status":"422"}`. The error names no reason. A `GET` of the ruleset afterwards matched the copy saved before the call byte for byte, so nothing changed. The repository is public and owned by a user account (`owner.type: User`), not by an organization.
- Root cause: merge queues exist only for organization-owned repositories: "Pull request merge queues are available in any public repository owned by an organization, or in private repositories owned by organizations using GitHub Enterprise Cloud" (docs.github.com, managing a merge queue). W-44 was planned from a reading of the docs that found "no account-type restriction" because it missed that availability line. The research for W-44 checked how the rule is written, never whether this repository can have it. The research agent asked after the 422 found the line (`.scio/agents/122-merge-queue.md`).
- Fix: the owner dropped W-44 on 2026-11-15 (`.scio/approvals.md`), and `docs/WORKFLOW_V2.md` records the reason. The ruleset stays as it was: the `checks` status required on an up-to-date branch, which `scripts/land.py` updates.
- Sweep: every GitHub feature the workflow relies on, checked against a user-owned public repository: rulesets, required status checks, `gh pr update-branch`, the GitHub Actions jobs and the `v*` release workflow all run here today. Auto-merge is off by the owner's rule, not by availability. The `merge_group` trigger in `.github/workflows/ci.yml` (W-37) never fires without a queue. It stays because it is harmless, and it is ready if the repository moves to an organization.
- Guard: `.claude/templates/research-brief.md`, the W-09 research brief. Its first question asks whether this repository can have the feature, quoting the docs' availability line against the owner type, plan and visibility, before any question about how the feature behaves. `test_the_research_brief_asks_whether_this_repository_can_have_the_feature` keeps that question first.
