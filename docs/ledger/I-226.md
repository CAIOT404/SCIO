### I-226 · An edit meant for a worktree landed in the main checkout
- Found: 2026-11-15 · landing the fragments PR (#122) · the orchestrator's Edit call
- Symptom: an Edit of `.github/pull_request_template.md` meant for the worktree `.claude/worktrees/w122-frag` named the main checkout's copy, and succeeded there, because the main checkout holds the same file with the same text. The main checkout went dirty on `main`, and the worktree missed the change. `git status` in the main checkout showed it a few calls later.
- Root cause: the absolute path was typed by hand without the worktree's segment, and nothing checks an Edit's path against the session's worktree. The push gate judges Bash commands only, and a session switches between the main checkout and its worktrees all day.
- Fix: `git checkout -- .github/pull_request_template.md` in the main checkout restored it, and the edit was made in the worktree. The main checkout was otherwise clean, so nothing else was touched.
- Sweep: every Edit and Write of this session that named a path in the repository: the others named the worktree they meant. No other checkout or worktree had uncommitted changes nobody made on purpose (`git status --short` in each, listed by `scripts/session_state.py`).
- Guard: `scripts/hooks/worktree_guard.py`, a `PreToolUse` hook on `Edit|Write|NotebookEdit` in `.claude/settings.json`. When the session's `cwd` is a worktree, it refuses a write to the main checkout's tree and names the worktree's copy of the path. Writes in any worktree, outside the repository, and to ignored paths (`.scio/`) pass. A refusal is logged to `hook-refusals.log` (W-18). Tests: `test_a_worktree_session_cannot_write_the_main_checkouts_files`, `test_the_worktree_guard_allows_every_other_write`. Guardrail 99.
