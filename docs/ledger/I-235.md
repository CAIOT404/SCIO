### I-235 · A feature's design question stopped the whole build until the owner answered
- Found: 2026-11-15 · issue #141 part 5 (ADR 0020) · scio/product/build.py feature, _run_batch, _feature_decision
- Symptom: graphcalc M4: P29's coder asked a design question at 01:38 UTC (`design decision needed: ...`, thread `build-graphcalc-m4-p29-a1`). The build stopped at the feature decision (`retry`, `skip` or stop). The answer came at 03:30, and in those 1.9 hours nothing else in M4 built. The owner (#141): "Make questions to you a first-class, asynchronous channel ... Other features keep building in parallel while it waits. Your answer goes into the next attempt automatically."
- Root cause: `feature` and `_run_batch` sent every attempt that paused or failed to `_feature_decision`, one blocking interrupt for the whole build thread, whether the attempt asked a question or simply failed. The question reached the owner only in that interrupt's `ledger_tail`, and the answer only as `retry: <answer>` at the same stop (#137).
- Fix:
  - `asked_question` (what `stop_question` used to inline) finds the attempt's question. When there is one, `_park_record` ends the attempt's own interrupt with `PARK_REPLY` (`checkpoint_gate.halt` only notes a reply) and records `FeatureRun(status="parked", question, question_id)`. The serial path and every job of a batch do this.
  - The question's id is the attempt's thread id (`build-graphcalc-m4-p29-a1`; `questions.Question.qid`, the orchestrator's decision). A new build thread or a later milestone numbers attempts from 1 again, so `<feature>-a<attempt>` would let an old question's marker suppress a new post, and an old answer answer a new question.
  - `_ask` comments `questions.format_question` on the feature's issue with `GitHubClient.comment_once` and adds `needs-answer` with `add_label`, but only once the comment is there. Each write checks the world first. Offline, `_ask_offline` appends it to `.scio/product/issues/<id>.md` and commits it on the milestone branch (`[scio:question:<qid>]`).
  - Every GitHub write of the channel (question, label, receipt, label removal, deferral notice) goes through `_github_write`, which is best-effort (the orchestrator's decision). A `GitHubError` becomes a ledger line, and the effect stays started. `retry_github_posts`, at the top of every `answers` pass, makes it again: for each feature, the newest run that asked. The feature stays parked meanwhile, and the build never halts on GitHub.
  - `proceed` also takes each deferred feature's `needs-answer` off and comments that the owner deferred it to the next milestone (the orchestrator's decision).
  - `next_feature` passes a parked feature over; `ProductBuildState.parked_runs` lists the open questions.
  - A new node, `answers`, runs before every feature pass and before `integrate`. `pick_up_answers` reads `questions.parse_answer` over `GitHubClient.issue_comments`, else `questions.read_answer_file` in `answers_workspace` (the directory holding the run's `.scio`, the dashboard's `--root`). An answer turns the parked run into #137's retry record (`failed`, `decision="retry"`, `answer`; question and id kept), and with GitHub the label comes off and a received comment is posted. It is a node of its own because a node that interrupts re-runs from its top on resume, and an answer read there would change which feature the reply decides.
  - When only parked features remain, `answers` routes to the new node `questions_wait` (phase added to `ProductBuildPhase`): one interrupt listing every open question with its link. `proceed` records each as a skip (#140's gate defers it), `stop` ends the build, and anything else reads the answers again. `resume_build` replies `QUESTIONS_RERUN` when `scio build` is run again without `--decision` there.
  - The milestone PR body marks a deferred question (`skipped (question <qid> unanswered)`).
  - Accepted as they are, by the orchestrator's decision. Offline, the question's commit moves the milestone head, so a parked attempt's verified commits are not carried into its next attempt (#119); graphcalc runs `--gh`, where a question is a comment. A feature whose `depends_on` names a parked feature still builds, as after a skip.
  - A failure without a question still goes to `_feature_decision`, unchanged.
  - `decided_at_a_stop` covers a stop the old code already asked on a question. The build thread's pending interrupt names the attempt, so the node run that the owner's reply starts takes `_feature_decision` and consumes the reply. Without this, the attempt would park and the reply (`retry: <answer>`) would be lost unread.
- Sweep: `grep -rnE '_feature_decision\(|asked_question\(|\.status (==|!=|in) |status == "skipped"|"parked"' scio/ --include=*.py`. `_feature_decision` has two callers, the serial feature and the batch, and both park first. The status readers are `next_feature`, `finished`, `ready_batch` (parked is unfinished, so a batch holds its dependents back), `milestone_gate` (a parked feature never reaches it; after `proceed` it is a skip), `update_progress` (likewise), the PR body (now annotated) and `earlier_runs` (passes a parked run through). `scio/product/report.py` and the CLI print the status as text.
- Guard: `tests/unit/test_question_channel.py`, 12 tests. `test_a_stop_asked_before_the_upgrade_still_takes_the_owners_reply` fails with `decided_at_a_stop` switched off. `test_a_question_id_is_unique_across_milestones` fails with the `<feature>-a<attempt>` id. `test_a_failed_question_post_keeps_the_feature_parked_and_retries_next_pass` fails when a write raises. `tests/unit/test_questions.py::test_a_given_qid_is_the_question_id_everywhere` covers the contract. These 8 fail on the old code: `test_a_design_question_parks_the_feature_and_the_build_goes_on`, `test_the_question_is_commented_on_the_issue_with_the_needs_answer_label`, `test_an_answer_comment_gives_the_parked_feature_its_next_attempt_with_the_answer`, `test_an_answer_file_gives_the_parked_feature_its_next_attempt`, `test_the_build_reads_answers_from_the_directory_it_runs_in`, `test_the_milestone_waits_once_when_only_parked_features_remain`, `test_proceed_at_questions_wait_defers_the_parked_features` and `test_a_failure_without_a_question_still_stops_for_a_decision`. The 9th, `test_a_batch_parks_its_questioning_feature_and_merges_the_other`, was written after the change. There are also 3 client tests in `tests/unit/test_github_client.py`. Five existing tests pinned the old stop: test_retry_answer's three graph tests (now on a gate escalation or an idle coder, with the stop's own line as their question), the `escalate_human-interrupt` case of `test_feature_failure_stops_for_one_human_decision` (now `gate_verdict="escalate_human"`), and the #119 test (I-236).
